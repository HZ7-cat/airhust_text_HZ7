# 第二关绕圈任务说明
## 1. 实现方法
采用离散航点法。将完整圆周划分为 N 个航点，按照航点编号
逐个发送目标。只有无人机到达当前航点后，才推进到下一个航点。
（我使用12个航点）
圆周目标生成公式：
`x = center_x + radius * cos(theta)`
`y = center_y + radius * sin(theta)`
`theta = direction * 2*pi*k / N`
其中 k 从 1 到 N，k=N 时回到圆周起点。

## 2. 修改位置
- `template.yaml`：增加圆心、半径、航点数和方向参数。
- `template.cpp`：读取 YAML 参数，修改` case 2 `和 `case 3`，
  将原任务改为圆周航点任务。

## 3. 任务流程
case 1：起飞
case 2：到达圆周起点
case 3：按顺序绕行 N 个航点
case 4：悬停 3 秒
case 5：降落
## 4. 数据就绪条件
程序等待飞控` connected` 和 `OFFBOARD`，并通过
`/mavros/local_position/odom `接收位置反馈。
`local_pos_cb()` 保存最新位置，`ros::spinOnce()` 执行回调。

## 5. 绕圈推进和完成判断
`mission_pos_cruise()` 返回 true 后，`circle_waypoint_index `加一。
当编号大于` circle_waypoints `时，说明已经经过第 N 个点并回到起点，
进入悬停阶段。

## 6. 参数
```
circle_center_x: 1.0
circle_center_y: 0.0
circle_radius: 1.0
circle_waypoints: 12
circle_direction: 1
err_max: 0.15
```

## 9. 遇到的问题
问题 1：`Gazebo`启动时 `gzserver `崩溃
启动第二关仿真时，`Gazebo` 弹出提示：
```
Sorry, the program "gzserver-11.15.1" closed unexpectedly
Your computer does not have enough free memory...
```
随后` sim.launch` 中无法继续获得正常的仿真环境，`PX4 `和` MAVROS `也不能正常使用。
原因
`Gazebo `启动时发生内存不足或瞬时资源占用过高，导致` gzserver` 异常退出。该问题与 `template.cpp` 中的圆周代码无关
修正方法
关闭其他占用内存的程序，并重新启动仿真
 问题 2：PX4 周期性时间跳变,PX4 日志周期性出现：
```
TM : Time jump detected. Resetting time synchroniser.
WARN [mc_pos_control] invalid setpoints
WARN [mc_pos_control] Failsafe: stop and wait
```
时间跳变约每 49 秒出现一次，随后影响位置目标。
检查 Gazebo 时钟：
`/clock` 持续保持约 `1000 Hz`，说明 Gazebo 仿真时钟稳定。进一步检查 MAVROS 配置，发现默认启用了 PX4 时间同步。
处理:
在 `/home/airhust/airhust_ws/src/simulation/config/px4_config.yaml` 中设置：
```yaml
conn:
  heartbeat_rate: 1.0
  timeout: 10.0
  timesync_rate: 0.0
  system_time_rate: 0.0
```
重启仿真后，MAVROS 参数显示：
```text
/mavros/conn/timesync_rate: 0.0
```
本任务只使用位置和速度控制，不依赖 MAVROS 时间同步。
问题 3：`case 3` 中 else 与错误的 if 配对
现象
修改圆周航点代码后，程序可能在无人机还没有到达第一个圆周航点时，提前进入：
完成一整圈，进入悬停
随后 mission_num 从 3 变成 4。
原因
else 遵循“与最近的未配对 if 配对”的规则。错误结构中，`else` 实际对应的是：
`if (mission_pos_cruise(...))`
而不是表示“航点是否还有剩余”的：
`if (circle_waypoint_index <= circle_waypoints)`
因此 `mission_pos_cruise()` 第一次返回 false 时，程序误以为所有航点已经完成。
修正方法
先关闭内层到达判断，再关闭外层航点数量判断，最后让` else` 与外层` if` 配对：
`mission_pos_cruise() `返回 `false`：保持当前航点，下一轮继续检查。
` mission_pos_cruise() `返回 `true`：推进到下一个航点。
 所有航点完成：进入悬停。

问题 4：圆周角度公式误写成乘法
现象
程序能够不断打印圆周航点，但所有目标位置都集中在圆周起点，无法形成完整圆形轨迹。
原因
圆周航点角度原应表示“第 k 个航点占整圈的比例”，正确形式是：
`theta = direction × 2π × k / N`
错误代码使用了乘法：
```
float theta =
    circle_direction * 2.0f * M_PI *
    circle_waypoint_index * circle_waypoints;
```
例如` N = 12` 时：
`k = 1：theta = 24π`
`k = 2：theta = 48π`
这些角度都是整圈的整数倍，计算出的 `sin(theta)` 和 `cos(theta) `基本相同，因此所有航点都回到了同一点。
修正方法
将乘法改为除法：
修正后，不同航点具有不同的角度：
```
k = 1：theta = 30°
k = 2：theta = 60°
k = 3：theta = 90°
```
也可通过日志检查前几个目标是否逐渐改变位置。

问题 5：修改` YAML `后程序仍使用旧参数
现象
修改` template.yaml `中的圆周半径或航点数量后，重新运行程序，轨迹没有发生变化。
原因
YAML 文件不会自动同步到正在运行的程序：
修正方法
每次修改 YAML 后执行：
`rosparam load src/template/config/template.yaml`
然后重启节点：
`rosrun template template`
需要区分：
修改 .cpp 或 .h → `catkin_make`
修改 .yaml       →` rosparam load + 重启节点`
问题 6：程序显示降落完成，但无人机仍处于解锁状态
现象
程序终端显示：
`Precision landing complete.`
但检查飞控状态时出现：
```
armed: True
mode: "POSCTL"
```
或者无人机的高度还没有回到地面附近。
原因
当前` precision_land() `主要通过等待 5 秒来判断降落流程完成：
它没有检查：
- 无人机是否已经触地
- 当前高度是否接近地面
- PX4 是否已经上锁
因此“函数计时结束”不等于“物理降落完成”。
排查过
程序结束后检查：
rostopic echo -n1 /mavros/state
rostopic echo -n1 /mavros/local_position/odom/pose/pose/position
重点查看：
armed: True/False
以及 position.z 是否接近地面高度。
修正方法
测试或演示结束后必须确认：
armed: False
